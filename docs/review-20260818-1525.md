### 검토 사항 (표준 영역)

표준 영역은 위반이 아니라 **발견 사항**으로 보고한다.

1. **`ExceptionController`를 `10_LOGGING_AND_EXCEPTION.md` §6 기준으로 작성 (레퍼런스 구현과 다름)**
   - 발견: 레퍼런스 `todo-app/backend`의 `ExceptionController`는 `NotFoundException`과
     `DuplicatedException`을 **`ResponseEntity.badRequest()`(400)로** 반환한다.
   - 영향: `10`은 `NotFoundException` → **404**, `DuplicatedException` → **409**를 요구하고,
     "상태 코드 잘못 매핑"을 명시적 금지 패턴으로 든다. 레퍼런스 쪽이 표준 문서와 어긋난다.
   - 판단: 문서(`10` §6)를 따랐다. 응답 포맷도 `traceId`/`status`/`code`/`path`/`method`/
     `timestamp`/`fieldErrors`를 갖춘 §6 스펙을 채택했고, 4xx는 `log.warn`(stacktrace 미포함),
     5xx는 `log.error`(stacktrace 포함)로 분리했다.
   - 의도 가능성: 레퍼런스가 구버전 MmsServer 코드를 그대로 옮겨온 것일 수 있다. **팀 확인 필요.**

2. **`AspectLogger`에서 사용자 클레임 로깅 생략**
   - 발견: 레퍼런스는 `JwtAuthenticationToken`에서 `idx`/`user_name`/`profileName`을 뽑아 찍는다.
   - 영향: 이 프로젝트에는 Spring Security가 없어 해당 코드가 컴파일되지 않는다. 상태코드·소요시간·
     INPUT/OUTPUT 로깅은 동일하게 유지했다.
   - 의도 가능성: 인증 도입 시 레퍼런스 형태로 복원하면 된다.

3. **`AspectLogger`의 `startTime`을 `ThreadLocal`로 변경**
   - 발견: 레퍼런스는 싱글턴 빈의 **인스턴스 필드** `private long startTime`에 시작 시각을 담는다.
   - 영향: 동시 요청 시 다른 요청이 값을 덮어써 소요시간이 뒤섞인다. `ThreadLocal`로 바꾸고
     `logOutputData`에서 `remove()`한다.
   - 의도 가능성: 측정값이 근사치여도 무방하다고 판단했을 수 있다. **팀 확인 필요.**

4. **커스텀 예외가 `super(message)`를 호출하도록 변경**
   - 발견: 레퍼런스는 `@AllArgsConstructor`로 `information` 필드만 채워 `getMessage()`가 `null`이다.
   - 영향: `10` §6이 요구하는 로그/응답 메시지가 비게 된다. 명시적 생성자로 `super`에도 전달했다.

### 구동 검증에서 발견해 수정한 것 2건

1. **`HttpMediaTypeNotSupportedException`이 500으로 나갔다** (🔴 High)
   - 증상: 잘못된 `Content-Type`으로 POST하면 catch-all `@ExceptionHandler(Exception.class)`가
     받아 **415가 아니라 500 `INTERNAL_ERROR`** + stacktrace를 뱉었다.
   - `10_LOGGING_AND_EXCEPTION.md`의 금지 패턴 "모든 예외 500으로 묻기"에 해당.
   - 수정: `ExceptionController`에 `HttpMediaTypeNotSupportedException` → 415 `UNSUPPORTED_MEDIA_TYPE`,
     `HttpMediaTypeNotAcceptableException` → 406 `NOT_ACCEPTABLE` 핸들러 추가.

2. **PUT 응답의 `modifyDate`가 갱신 전 값이었다** (🟡 Medium)
   - 증상: DB의 `modify_date`는 갱신되는데(확인함), **응답 본문에는 갱신 전 값**이 실렸다.
     `@LastModifiedDate`는 flush 시점에 찍히는데 `save()` 직후 `toResponseDto()`가
     커밋 전에 실행되기 때문. 클라이언트가 응답값을 그대로 캐시하면 DB와 어긋난다.
   - 이 형태는 `05_SERVICE_GUIDE.md`의 UPDATE 템플릿 및 레퍼런스 구현과 동일하다 —
     **표준 템플릿 자체가 가진 문제**로 보인다. **팀 확인 필요.**
   - 수정: `todoRepository.save(entity)` → `saveAndFlush(entity)`.
     메서드 구조·네이밍은 표준 그대로 유지하면서 응답과 DB를 일치시킨다.
   - 회귀 방지 테스트 추가: "수정 응답의 modifyDate가 갱신 전 값이 아니라 갱신된 값이다".

## 확인 필요 (동작 변경)

정렬 과정에서 **API 계약이 바뀌었다.** 프론트엔드가 붙어 있다면 함께 수정해야 한다.

- 엔드포인트 `/todo` → `/api/todos`, 모든 요청에 `X-API-VERSION: 1` 헤더 필요
- 응답 필드 `id` → `idx`, `createdDate`/`modifiedDate` → `registerDate`/`modifyDate`
- 응답 필드 **`url` 삭제**
- 목록 조회 응답이 `List` → `Page` (`content`/`totalElements` 래핑)
- 수정이 `PATCH` → `PUT`
- 삭제 응답이 `204 No Content` → `200` + `{"result":"TRUE"}`
- 404 응답 본문이 Spring 기본 포맷 → `ExceptionResponseDTO`
